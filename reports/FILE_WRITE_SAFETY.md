# Exact small-file create/write/append and one-level directories

## Scoped implementation

`ultron/actions/file_controller.py` create_file/create_folder/write_file (including direct helpers) route to `ultron/core/file_mutations.py`. The immutable, single-use host-approved plan binds absolute target, action/append intent, existing immediate parent identity, exact current regular-file fingerprint and complete before/after bytes. The effect sink consumes that exact grant, rechecks current roots/parent/target, then mutates. No input approval flags/tokens. Headless, denied, cancelled, expired and replayed approvals do not mutate. Existing write/append no longer truncate in place. New files require vacancy; create_file never overwrites. Parent directories must already exist. Folder creation is one level only, rejects existing targets and does not implicitly create ancestors.

Small-file limit is now **16000 bytes** for input, existing content and result, including UTF-8 expansion and append totals. This is an intentional reduction from the old 1MB behavior, to keep complete before/after base64 snapshots inside the operation primitive's 64KiB JSON plan ceiling. Existing binary content can be replaced/append-preserved and restored byte-for-byte; supplied content must be UTF-8 encodable text. Full supplied text is JSON escaped in the approval, alongside exact path, old identity and result size/hash. Append binds old bytes, not whatever happens to exist at approval time. Old bytes are read locally to build/validate the plan before consent; this adapter does not send them to a provider. Hashes/paths and user-supplied content are visible to the approval surface; existing outside model/UI/logging behavior is unchanged.

Publication uses a private same-directory `.ultron-write-*.part` tempfile, bounded content, fsync and fingerprint verification. Newly absent files use no-clobber hard-link publication (unsupported filesystems fail, no weak fallback). Existing files use `os.replace` only after final exact precondition checks. Final published fingerprint must match staging. Never delete a destination as failure cleanup; observed replacement staging inodes are not deliberately deleted. Cleanup failure can leave private temporary content and a completed destination while reporting unknown outcome. Check both paths/staging before manually retrying. No retry, automatic rollback, open or execution of the destination is performed. Scripts/config files can nevertheless be consumed by other applications, so approval explicitly warns about indirect effects.

## Undo

Successful effects register private inverse closures with the existing exact-entry session undo registry. Registry approval is separate and includes full path and expected identity plus previous size/hash/absence. The inverse requires a consumed session.undo callback context, current allowed roots, identical immediate parent, unchanged published file identity and (for directories) identical directory identity plus emptiness. Existing-byte restoration also stages/fsyncs/checks before replacement. New-file inverse only unlinks an unchanged created file. Folder inverse only rmdir's the unchanged empty directory, never recursively. Changed/replaced/occupied/populated targets or changed parents refuse; failing inverses are consumed, not retried. Byte restoration does not restore original inode metadata or hard-link relationships. The legacy `_undo_write` helper now fails closed rather than exporting an unapproved raw write callback. Legacy `_undo_create` remains for downloads and is explicitly outside this batch.

Private publication helpers require an already-consumed compatible grant context, checked via the narrowly documented operation_policy.require_consumed helper. It does not issue another grant, approve an independent operation or guarantee that arbitrary trusted callback code is a safe inverse. These are application call-path safeguards, not protection against malicious Python accessing private internals/replacing dependencies. Other original callbacks are not upgraded by this helper.

## Compatibility and limitations

- Existing writes replace a directory entry using a new private inode. They may change mode/owner/ACL/xattrs/ADS/metadata and detach this path from existing hard links. Other hardlinks retain their original bytes. This is disclosed, not silently described as metadata-preserving. New files/directories use private modes where supported; Windows semantics differ.
- Check-to-replace/unlink races remain. `os.replace` is atomic publication, **not compare-and-swap**: an external writer can change the target immediately after the last check. Path/parent replacement can race descriptor opens, link/replace, rmdir/unlink and staging cleanup. Immediate parent identity is not a complete ancestor-chain identity. There is no OS filesystem sandbox, cross-process lock, transaction, guaranteed rollback or adversarial concurrent-writer protection.
- Local shared safety lock serializes these code paths, not every file producer or external process. Hashing/reading/fsync/replace have no hard wall-clock deadline or interruptible cancellation after execution starts; some shared fingerprint paths may read up to their larger 64MiB cap during a concurrent growth race. Native blocking remains possible.
- Before/after content and inverse snapshots live in memory (session undo depth 10); no encryption/secure erase/durable journal/crash recovery/shutdown admission barrier. A crash or cleanup failure can leave staging/committed files without an undo entry. Lack of an undo entry never proves no mutation occurred.
- Default roots still include home, not a dedicated data sandbox. Root policy, runtime, callback code and filesystem/native semantics remain trusted. Existing rich approval UI behavior/long-content rendering has not been native-tested; backend binds the full snapshot regardless.
- **Delete/Trash, automatic restore-from-Trash, downloads receive/publication, legacy download `_undo_create`, unrelated plugins/macros/Git writers and other producers remain unmigrated.** No claim of universal file permissions or whole-app safety. Directory batches stay disabled; read-only organization preview remains available.
